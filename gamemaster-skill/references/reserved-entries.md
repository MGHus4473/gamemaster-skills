# 预留名额与真实选手替换

预留是未来可替换的报名席位，候补是真实申请人等待名额，轮空是无需实际对阵的签位，三者分别建模。用户明确需要时，在并组去向和真实人数确认后、正式竞赛方案和抽签前加入；一般每单项讨论1～3个，不默认所有项目都加。单打1项是1人，双打1项是完整1对，团体1项是1队。

## 选择数量

先问预计补录量、每项上限、资格范围、截至何时、如何分配席位、未填怎么办、是否允许改签表与延长时间。数量取满足需要的最小值，对0～3项分别报告：真实项数、计划项数、签位/各组容量、额外实际比赛、轮次及占场估计，避免为少量补录大幅扩大赛制。

| 赛制 | 增加k项的影响 | 决策要点 |
|---|---|---|
| 冠军单淘汰 | n−1变为n+k−1；三四名赛在适用时另加1 | 优先比较当前签位中的空余容量；跨8/16/32等边界会增加最大轮次，但不表示实际比赛翻倍。仍需遵守轮空分配与种子规则。 |
| 全组单循环 | 多出kn+k(k−1)/2场 | 8人增加1/2/3项多8/17/27场，常比淘汰更昂贵。 |
| 分组循环接淘汰 | 对调整后的各组分别算nᵢ(nᵢ−1)/2，再算晋级阶段 | 优先比较固定组数下小组均衡方案；确认预留是否导致出线率差异、跨组比较和保障场数变化，不能为省场直接改晋级数。 |

成本按“全部预留填满”测算，占场时间还要经过休息和依赖排程才能证明放得下。空预留不能承诺保证几场真实比赛。原人数未达开赛门槛时先并组/调整/确认例外，不能用占位凑8人。

```bash
python scripts/registration_transition.py scenarios 测算输入.json 测算结果.json
```

输入`real_count`、`max_reserve`（通常3）、`config`。`format`可为`round_robin`、`knockout`（可带`bronze:true`）、`groups_knockout`（须给`groups/advance`及可选`bronze`）。完整取前8名时明确`classification_places:8`和`bronze:true`，且淘汰阶段至少8项；测算另计5—8名附加赛的4场。只支持固定组数、均衡分组和一致晋级；前8之外的全名次赛、不均衡固定组、特殊轮空、团体子场等需按实际结构另算。

## 数据与抽签

预留项使用稳定且唯一的报名项ID、`kind:placeholder`、中文标签`预留名额-项目-序号`、`members:[]`。不编造姓名、身份证、手机、性别、年龄或俱乐部，也不设种子。保留预留政策：资格、替换期限、分配方式和空位处理。

本地名单Excel按现有模板输出：单打名额一行；双打一对一行，显示同一名额的A/B位，性别/身份留空，明确不是两位已报名选手。汇总分别显示真实项、预留项、计划项及已知运动员数。预留不能出现在真实收费/到场/奖励人数中。

转本地抽签输入时使用标签为`name`、空字符串`club`、`seed:0`和原ID。未知单位不参与回避，只保证已知单位；不是将预留项分配给一个叫“预留名额”的俱乐部。记录签位与预留ID关系，替换真实选手后更新展示名而保留此关系。平台导入当前未验证这种空身份结构；`participant_roster.py --system`会明确拒绝未填预留，不为通过导入而填假性别。

## 替换与截止处理

替换必须关联真实报名记录，核查资格和搭档、截止时间、缴费/确认状态、同人重复、兼项上限、同单位回避、让分类别及所有相关项目的时间冲突和休息。补录分配按事先确认的顺序/随机办法，不按已公布对手挑选有利签位。若出现种子或回避冲突，明确可选择拒绝该席位、使用其他合规预留位或按批准规则调整；不自动重抽。

`registration_transition.py replace 名单.json 预留ID 实际补录.json 新名单.json`保持原entry ID和签位元数据，写入真实成员及真实报名ID，真实计数+1、预留计数−1、计划总数不变，保存前后记录。输出`reviewed:false`，完成名单/抽签/排程联动复核后再导出。调用者应先查系统开赛状态，脚本不连接平台检查；已开赛或已计成绩的席位不得作为未使用预留直接替换。增加新让分类别需修订完整矩阵和补充通知，不只给新选手填一个分值。

未填名额：抽签前可按确认政策删除并重算方案；抽签后按政策转为轮空或弃权，记录真实对手无需比赛的晋级，不能生成虚构比分。循环赛要明确剔除空位、保障场数以及同分/跨组排名口径；不能把“空位输21:0”自动计入净胜分。移除后核对晋级与上下游依赖、领奖人数和时间表版本。
