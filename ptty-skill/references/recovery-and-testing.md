# 操作合同、恢复与流程验收

本参考用于批量写入、超时重试、临场变更和功能回归。工具只核对本地事实，不登录、不调用接口、不授予执行权限。用当前任务授权和页面证据决定实际操作。

## 字段与任务合同

每项写操作先形成以下记录，存入赛事工作区：

|部分|必须记录|
|---|---|
|目标|赛事明文ID、运动模块及枚举、项目/阶段/场次/小节、受众|
|页面合同|路由、组件、接口及增改删模式、客户端文件名/哈希、角色、观察时间|
|字段|类型和枚举、必填条件、页面初始值、当前值、拟修改值；空值与缺失分开|
|提交语义|增量或整表覆盖、是否级联、重复提交效果、费用/通知等副作用；未知须补查|
|验收|全量读取入口、稳定业务键、应变化字段、应保留字段、下游复核对象|

以[创建发布](publication.md)等专题的已核验合同为起点，每次依当前页面补齐；操作目录的 `requires` 不是接口必填字段。既有赛事优先保留当前值，不能用新建表单默认值覆盖。服务端ID由创建后的唯一对象回读绑定；同名多项时不能凭第一条绑定。

`scripts/task_contract.py` 检查智能体提出的动作是否落在结构化任务范围内：

```json
{
  "contract": {
    "event_id": "synthetic-event",
    "allowed_operations": ["schedule.move"],
    "required_operations": ["schedule.move"],
    "project_ids": ["P1"], "match_ids": ["M1", "M2"],
    "protected_match_ids": ["M1"], "audiences": [],
    "allowed_fields": {"schedule.move": ["time", "court"]},
    "readonly": false, "protect_existing_results": true
  },
  "actions": [{"operation_id": "schedule.move", "event_id": "synthetic-event",
               "project_ids": ["P1"], "match_ids": ["M2"],
               "changed_fields": ["time"]}]
}
```

`python scripts/task_contract.py 任务合同.json`：退出0为结构合格，1为动作越界/缺项，2为输入无效。受约束的写操作须列出实际对象与受众；不接受通配符。字段名是该合同定义的精确路径，应与实际请求差异一致。工具不解析原始自然语言、不验证授权真实性，也不检查未建模的字段语义。提交前仍逐项对照用户原话及完整请求，不能自行扩大 `allowed_operations` 让候选通过。

## 快照比较与恢复

1. 提交前保存完整作用域快照、拟定结果和文件哈希。投影包含所有受影响及必须保留的字段；不能只比较拟改的一列。分页未读完或只看到筛选结果时 `complete:false`。
2. 一次提交后刷新直接结果和必要下游。超时、HTTP成功、页面成功提示均不能证明落库状态。
3. 用 `workflow_state.py` 比较三份快照。稳定 `key` 不用姓名或可变行号；新建赛事先以工作区唯一操作键关联，拿到且确认唯一服务端ID后另存映射。
4. 只对仍与基线完全一致的未完成行讨论补交。整表覆盖接口不得提交剩余行子集；须重读完整表、保留新值后重新形成候选和验收范围。
5. 行部分更新、出现其他人的修改或非预期默认值时停止覆盖，定位差异。没有新证据不反复提交；已经成功的行不重复新建。收费、退款、通知发送先核对流水/送达记录，不能按普通数据导入自动重试。

导入响应`isSuccess:true`可能同时带成功和失败条数。核对业务消息、目标总数及逐行回读；曾观察三行方案显示成功2条/失败1条（同标题提示“项目已存在”），但目标完整列表仍为空。此时不能宣称两条已正确落库，也不能直接补交失败行或重传整表；先核对唯一键、阶段、导入赛事绑定和实际落库位置。没有可见稳定业务键时保留待查，运动标签异常的豁免也不覆盖这类功能失败。

### 方案导入异常的页面恢复路径

2026-10-08在无既有项目、名单和场次的隔离合成赛，确认上传与读取绑定同一赛事且完整列表仍为空后，使用当前页面新增合同恢复成功。此证据说明可继续创建流程，**不证明 Excel 导入器已修复，也不证明此前报告成功的行去了哪里**。真实赛事存在未明数据时先查清影响范围，不能照搬测试赛的空基线。

1. 重新取得无筛选全量方案及相关名单/场次，保存基线。将恢复候选限定为已确认缺失的项目；已有行逐字段保留，不删除或整表覆盖。
2. 当前 `TrialGhIndex` 的 `addXm()` 初始化模型，提交到 `ssghGl/insertOrUptOrDel`，使用 `TYPE:ADD、SETLX:ADDXM` 新增第一阶段。赛制、人数、组数、晋级、计分等来自确认方案，其余字段取当前表单合同；每次提交后回读唯一 `XMID`。
3. 从刚回读的第一阶段行执行页面 `addTwoJd(row)` 初始化后续阶段。已核验合同为 `TYPE:ADD、SETLX:SINGLESETJD2`，`XMIDS` 引用前阶段真实ID；同时核对 `XMBH/JD/FJ`、晋级总人数和 `QJDZS/QJDQSMC/QJDJZMC`。给阶段明确名称，保留名称映射；同标题导入曾报重复，但不能据此认定改名即可修好 Excel 导入。
4. 各行成功后重新比较全部方案，再在授权范围核验下游。方案恢复阶段取得3条方案、21场结构及8人单打/5对双打名单，轮次、轮空和决赛/季军赛胜负路径通过；实际成绩推动的分组晋级须单独核验，后续覆盖范围见本页末尾实测记录。

一次提交失败、列表缺失或出现非预期差异就回到快照比较；这些参数仅代表所述页面版本，不能作为脱离当前合同的通用重试脚本。方案恢复不自动授权收费锁定、重抽、重建已有场次或发布。

### 快照输入与判定

输入结构（均为本地投影，字段值不含凭据）：

```json
{
  "schema_version": 1, "operation_id": "schedule.move", "input_version": "synthetic-v1",
  "before": {"binding": {"event": "synthetic-event", "scope": "P1"}, "complete": true,
             "captured_at": "2030-01-01T10:00:00+08:00",
             "rows": [{"key": "M1", "values": {"time": "11:45", "court": 1}}]},
  "desired": {"binding": {"event": "synthetic-event", "scope": "P1"}, "complete": true,
              "rows": [{"key": "M1", "values": {"time": "11:30", "court": 1}}]},
  "current": {"binding": {"event": "synthetic-event", "scope": "P1"}, "complete": true,
              "captured_at": "2030-01-01T10:02:00+08:00",
              "rows": [{"key": "M1", "values": {"time": "11:45", "court": 1}}]},
  "attempts": 1, "submitted_at": "2030-01-01T10:01:00+08:00",
  "policy": {"subset_retry_verified": true, "irreversible": false, "downstream_required": false},
  "evidence": {"session_valid": true, "contract_current": true, "transport": "timeout"}
}
```

```bash
python scripts/workflow_state.py 恢复输入.json --out 新比较结果.json --journal 操作回执.jsonl
```

|状态|下一步|
|---|---|
|`prepared`|候选与当前基线一致，可继续实际提交前的合同核对|
|`matched_desired`|投影已吻合，不补交；按独立在线证据报告验收层级|
|`readback_required`|补读完整、未过期且晚于提交的状态|
|`contract_recheck_required`|当前接口/版本尚未核实，先补证据|
|`conflict_review_required`|出现非预期变化，查明后重新确定基线和目标|
|`subset_retry_candidate`|只有 `retry_keys` 仍未生效；确认增量语义并再次刷新后才可补交|
|`retry_contract_required`|未证明接口支持子集补交，不提交残余表|
|`retry_limit_requires_new_evidence`|已尝试至少两次，先取得能解释失败的新证据|
|`transaction_reconciliation_required`|核对交易或发送流水，不盲目重试|
|`downstream_readback_required`|直接字段一致，晋级/排名/客户端等下游仍待核验|

所有输出固定 `execution_authorized:false, online_verified:false`：工具无法证明输入来自在线读取。`new_evidence:true` 必须另附实际新证据说明，不能作为重试开关循环设置。哈希日志能发现已有链条改动，不能证明来源可信，也不支持并发写入；按赛事串行执行。日志中的业务键仍可能关联赛事，只保存在私有工作区。

## 临场变更的验收对象

|变更|执行前及回读后必须核对|
|---|---|
|替补、改搭档|替换资格/截止时间、报名项与成员ID、兼项、种子、已开赛范围；重算受影响冲突，不自动重抽|
|取消/并组|原组到目标组映射、已收费/退出事实、方案容量、名单、签位、附加规则和补充通知；退款另按授权处理|
|调场、提前、延误|保留原场次ID/比分，检查前后依赖、跨项人员、休息、固定场次、小节与各端展示；验收离线引擎的目标指标|
|比分纠正、弃权|保存原结果、明确裁定依据，检查晋级分支及已开赛后继；受影响赛程/排名/证书重新验收，不静默覆盖|

## 流程与意图回归

完整流程拆为：基础资料 → 报名/名单 → 竞赛方案 → 场次/签位 → 编排 → 小节 → 成绩 → 导出。已有合格节点可复用；每步记录输入、直接回读、下游验证和保护字段。新建无收费、无通知的隔离合成赛事用于获授权写入测试；执行前核对作用域，遇到收费/通知等超出任务范围时先准备具体影响说明。

仓库 `tests/test_workflow_pipeline.py` 使用纯合成报名项，串联循环、淘汰、两阶段共26场的名单/方案Excel、抽签、对阵、编排验收、结构化赛果、排名导出、交接哈希核验。团体仅核对总比分，现有通用名单引擎不接受团体项目，不能宣称团体全流程已通过。离线回归不能替代平台写入回读。

意图回归至少包括下列自然说法；分别产出动作计划，对照原话人工复核，再运行结构化合同检查。已有六类边界自动测试验证的是合同执行，不是语言模型理解准确率。

|用户输入|应执行/保护|需要澄清时|
|---|---|---|
|“只公布P1名单，其他不动”|只变名单可见性；保护其他项目、报名及通知|“公布”是展示还是消息发送不明时|
|“M2提前，别动M1和比分”|只调整M2；保留场次ID及结果、核对休息|固定安排/时间目标缺失时|
|“发布这份补充通知”|保存确认正文，核对受众；不自动发送消息|通知页面/强制弹窗未明确时|
|“第二小节只给手机端看”|修改指定小节手机开关，保留裁判和出场名单端|小节对象不唯一时|
|“报名改到另一个组”|定位报名映射及相关方案变化；不自动退款|源/目标、资格、让分及已开赛范围不明时|
|“某场成绩录错了”|比分修正与晋级重算分别验收|正确比分、裁定来源或已开赛后继处理不明时|

验收报告明确静态合同、本地回归、当前页面只读、实际写入回读四种证据。按“接口＋字段组＋模块＋角色＋版本”记录覆盖；单项成功不能把整类109项操作标成实测。资源哈希、枚举或回读形态变化时，降级相关操作的已验证标记并复核，不能沿用旧快照继续写。
